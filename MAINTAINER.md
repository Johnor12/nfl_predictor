# MAINTAINER

Technical map of the project. Read a directory's README.md for its API, and its MAINTAINER.md for its files.

## layout

The folders follow the architecture in README.md:

- README.md: project goals, concepts, and phases (plain text, edited by hand only).
- .claude/rules/general.md: working rules for agents.
- .claude/keepalive/: keeps the codespace awake while Claude Code is working, through the hooks in `.claude/settings.json` (`node .claude/keepalive/keepalive.js status`).
- pyproject.toml / uv.lock: Python 3.12+ project managed with uv (pandas, pyarrow, lightgbm; pytest for dev).
- events/: one package per event: its output type, and under `predictors/` one package per implementation (`baseline/` for all 21 so far: 17 play events, `coin_toss`, `toss_choice`, `timeout`, `challenge`), with a priors file per season from 2011 on, counted week by week. Also `baseline_priors.py`, which rebuilds every baseline's priors. Seven events have a second implementation, `gbm/`, that is their default: a trained model for one part of the event, with a model file per season: `lineups` (the fourth-down decision), `offensive_formation` (shotgun or under center), `snap` (run or pass), `pass_rush` (throw, sack, or scramble), `target` (air yards), `pass_result` (complete, incomplete, or intercepted), and `carry` (the yards of a run and after a catch). `punt_kick` has one too (the distance, from the weather and the punter), which is not its default. Each event's `predictors/__init__.py` names its default (`DEFAULT`), and `events.predictor(event, name=None)` is how an implementation is looked up; `situation.py` (the play) and `strength.py` (who is playing) are the inputs the trained models share, and `training.py` builds the tables of real plays they are trained on and retrains them all.
- scenarios/play/: the play scenario: inputs, event chain (fake kicks and the fair-catch kick included), rules, enforcement, stats, validator, narration, outcome summary, and the `Predictors` bundle (`load_predictors`).
- scenarios/coin_toss/: the coin toss scenario: the toss, the winner's choice, and who kicks off (`run_coin_toss`).
- scenarios/game/: the game scenario: the coin toss, then plays until the final whistle, with the clock, timeouts, coach's challenges, halftime, overtime, injuries (their stoppages and emergency replacements), and disqualifications between them (`run_game`, `validate_game`, `load_game_predictors`).
- simulators/play/: runs the play scenario over many inputs and summarizes each outcome.
- simulators/game/: plays a game many times and presents the distributions (`simulate_game`, `forecast`).
- evaluators/sample.py: which games an evaluation covers: a fixed sample of games across seasons (`sample_games`, `EVALUATED`).
- evaluators/scoring/: the evaluators' shared toolkit: fair CRPS and Brier scores, the reference to beat, sim noise, PIT histograms, reliability (`Scorecard`).
- evaluators/play/: scores the play scenario and each event predictor against real plays (`evaluate`).
- evaluators/lines/: scores betting lines against results, and a simulator's distributions on the same lines (`lines`, `score_lines`).
- evaluators/game/: scores the game scenario against real games and the betting lines, and the timeout and challenge predictors alone (`evaluate`).
- evaluators/audit/: checks the play simulator against real plays (validity and reasonableness metrics) and writes a report.
- shared/rulebook/: season-versioned rule constants from 2011 on, overtime and challenges included (`rules_for(season)`), and which seasons share a set of rules (`same_rules`, `KICKOFF`, `TRY`).
- shared/priors/: the toolkit behind the count-based baseline predictors (sampling, buckets, player picking, building priors files per season and week, and pooling what was played before a game into its priors).
- shared/models/: the toolkit behind the trained predictors: fitting gradient-boosted trees (LightGBM) to a table of real plays, for a yes/no output, one of several classes, or the distribution of a number, and loading the model for a game's season (`models_of`, `fit`, `fit_number`, `draw`, `save_model`).
- shared/nflverse/: downloads and caches nflverse data (`load`) for 2011 on (`SEASONS`), every season in the same shape; turns real plays into play scenario inputs (`real_plays`, `real_samples`) and real games into game scenario inputs (`real_games`), with each player's recent snaps from the best on-field source the season has, and form: what every team, head coach, referee, and player did before the game (`form.py`).
- shared/lines/: betting lines: game lines from the nflverse schedule (`game_lines`) and DraftKings player props via ESPN (`player_lines`).

Not built yet: the season scenario (phase 2). Known gaps inside what is built are listed in `scenarios/play/RULES.md` and `scenarios/game/RULES.md`.

## dependencies

They point one way: evaluators -> simulators -> scenarios -> events (output types) -> nothing, with shared/rulebook, shared/priors, and shared/models below everything. Among the scenarios, game -> coin_toss and play.

- An event's `__init__.py` holds only its output type, so the play scenario can import it. The play scenario knows nothing about data or about any predictor implementation; `load_predictors` asks `events.predictor` for them by name, or for each event's default.
- Predictor implementations (`events/<event>/predictors/<name>/`) sit above the play scenario: they import its public API (`from scenarios.play import ...`) for inputs and helpers, and `shared.priors`.
- The game scenario runs the child scenarios directly (`run_coin_toss`, `run_play`) and bundles their predictors with its own two, `timeout` and `challenge` (`GamePredictors`). A play's outcome summary (`scenarios.play.summarize`) lives in the play scenario because the game needs it for its history.
- shared/nflverse is the one part of shared/ that isn't at the bottom: it imports `scenarios.play` and `scenarios.game` (it builds `PlayContext`s and `GameContext`s). shared/lines sits on top of it. Only `events/baseline_priors.py`, `events/training.py` and the predictors' `train.py`, the evaluators, the game simulator's CLI, and tests import them; the scenarios never do.
- evaluators/scoring imports nothing from the rest of the project; the other evaluators score with it.

## commands

- Tests: `uv run pytest -q` (about 90 seconds with the cache). The nflverse, audit, priors-build, play and game evaluation, and lines tests skip unless `.cache/` has the 2026 files (and the 2014, 2016, 2019, and 2025 ones, for the tests that use them).
- Forecast a game: `uv run python -m simulators.game 2026_10_NE_DET --sims 1000` prints win probabilities and the distributions of the score and the main stat lines (about 0.1 seconds per simulated game and core).
- Evaluate the game scenario: `uv run python -m evaluators.game` writes `evaluation_output/game_2021-2026.md`: 160 games sampled from the last six seasons (about 3 minutes on 16 cores, 8 on 6, 11 on 4; `--games 16 --sims 10` for a quick look, about 15 seconds; `--seasons 2026 --games 0` for every game of a season; `--games 480` to compare two versions, about 9 minutes on 16 cores; `--no-lines` to skip the betting lines; `--swap carry=other` for another implementation, `--swap snap=baseline offensive_formation=baseline` for the baselines instead of the trained models).
- Evaluate the play scenario and its event predictors: `uv run python -m evaluators.play` writes `evaluation_output/play_2021-2026.md`, on the same 160 games (about 3 minutes on 16 cores, 6 on 6, 12 on 4; `--games 16 --sims 20` for a quick look, about 20 seconds; `--swap carry=other` for another implementation).
- Score the betting lines: `uv run python -m evaluators.lines` writes `evaluation_output/lines_2021-2026.md` for the same games (downloads each game's props on first use).
- Audit: `uv run python -m evaluators.audit --season 2026` writes `audit_output/report_2026.md`.
- Rebuild the baseline priors: `uv run python -m events.baseline_priors` (every season from 2011, one file per season and predictor; about 20 minutes on 2 cores; `2026` or `2020-2026` for some of them). The first run downloads about 25 MB of nflverse files per season.
- Each week, after its games: `uv run python -m events.baseline_priors 2026` adds them to the priors (refresh the cached 2026 nflverse files first: `shared/nflverse/MAINTAINER.md`; a rebuild from a cache older than the committed files takes games out of them). A game is predicted from the earlier seasons and its own season's earlier weeks, so next week's forecasts only see this week once it's built.
- Retrain the trained models: `uv run python -m events.training` (every trained predictor's models for the six most recent seasons, each from the seasons before it; `2026` for one season's). The first run builds every training table in one pass over the real plays (about 3 minutes on 6 cores, cached in `.cache/training/`), the 54 models then take about 10. One predictor alone: `uv run python -m events.snap.predictors.gbm.train`. Once a year, after a season ends: `uv run python -m events.training <next season>`.
- `NFL_PRIORS_DECAY=0.5` in the environment tries another weight for older seasons. Any evaluator, the audit, and the simulators take it.
- In this environment `UV_INDEX` points at an unauthenticated private registry. Run uv with it unset: `env -u UV_INDEX uv ...` in bash, or `$env:UV_INDEX=$null` first in PowerShell.
- Under WSL the repo's `.venv` is the Windows one. Keep the Linux environment somewhere else (`export UV_PROJECT_ENVIRONMENT=~/.venvs/nfl_predictor`), and LightGBM needs the system's OpenMP library (`sudo apt install libgomp1`). An evaluator process takes about 1.5 GB, so 6 cores want 10 GB free.

## conventions

- Every play and every game must be reproducible from its seed: a predictor only draws from the `random.Random` it's handed, and never iterates a set (or anything else unordered) on the way to a draw.
- A refactor shouldn't change a single simulated play. Check by hashing a few thousand seeded plays (`describe_play` output and stats) and the audit's metrics before and after.
- A predictor change is measured, not eyeballed: run `evaluators.play` before and after and compare the event's rows (and the play scenario's), then `evaluators.game` for its effect on whole games and against the betting lines. Look at `mean` against `sim mean` first: a change can score better on every play and still shift what a game adds up to (the first yards models did, by a touchdown every other game). Both score the same fixed sample of games across seasons, so two runs compare case by case. The game evaluator's default (160 games, 100 sims) only shows a change of about 2.5% on the margin and 5% on the winner; for a smaller one, compare on more games, not more sims (`evaluators/game/README.md`). A game is predicted from what was played before it (the earlier seasons and its own season's earlier weeks), so the scores are out of sample.
- Each season is predicted with everything its data has, and nothing is held back to the level of the poorest season. Priors: a season's file holds only the keys its data supports, and a predictor pools each key over the earlier seasons and weeks that have it (on-field personnel from 2016 on, charting from 2022 on; a 2026 game gets both from the seasons that have them). Inputs: a field only some seasons can fill (`Player.snaps` by kicking unit) is filled where they can, and the predictor falls back where it's empty. A new data source goes in the same way: through `shared.nflverse` into an input or a `Sample`, counted by the `priors.py` of the events it informs.
- A player's own season moves a baseline's rate toward his own: `Player.stats` (his season to date, from `shared.nflverse`) against the league's or his depth chart role's rate, shrunk by how much he has played (`shared.priors.usage` for carriers and targets, the pass rush baseline's `_dropback` for sacks and scrambles). Another one goes in the same way: the stat in `shared/nflverse/contexts.py`'s `SEASON_STATS`, one hand-set number of plays at which his season counts as much as the prior, and a before and after on the game evaluator's player rows. Anything richer than a shrunk rate is a job for a trained model.
- Who is playing reaches a predictor as form: what a team, a head coach, the referee (`Game.form(who)`), or a player (`Player.stats`, `Player.career`) did before the game, as totals for this season so far and for the earlier seasons (`shared/nflverse/README.md`). A trained predictor turns the ones it needs into rates (`events/strength.py`) and its model weighs them: there is no rating of a team or a player anywhere, only what it did and a model of what that predicts. A model gets few of them and reads most of them coarsely, and an input about who is playing is judged on a team's totals over a game as well as on the play. `events/MAINTAINER.md` has why, what each one is worth, what it came to in whole games and against the betting lines, and what was tried and left out (the coaches, the referee, the surface, a neutral site, the draft pick, and the weather).
- A trained predictor (a model instead of counts) keeps the same out-of-sample rule as the priors: a season's model is fitted to the seasons before it (`shared.models.models_of`), and its features and settings are chosen on seasons before the evaluated ones. It reads its inputs through one `features` function for training and predicting, replaces only the part of its event that it predicts (the rest stays the baseline's), and is measured like any other change. `events/MAINTAINER.md` has the pattern; `events/snap/predictors/gbm/` was the first. Its settings too: the rounds of the three-class models were set on 2019 and 2020.
- A trained predictor may read what an earlier event of the play decided (the snap reads the personnel group, the shotgun, and the box) only once that event's predictor is good enough to feed it: it is trained on the real value and handed a simulated one. The play evaluator shows both sides: an event's own rows are scored on the real play's recorded inputs, `play: ...` on what the chain produced itself.
- An implementation that measures better than an event's default becomes it: `DEFAULT` in `events/<event>/predictors/__init__.py`. The evaluators, the audit, and the simulators run the defaults, so the reports in `evaluation_output/` are the current system's; `load_predictors("baseline")` is still every event's baseline.
- The betting lines before a game are inputs (`Game.spread`, `Game.total`), for what the lines themselves might cause (README.md: the referees, through fouls), not for borrowing the market's forecast of the game. No predictor reads them yet: they were tested in the run-or-pass model and left out (`events/snap/predictors/gbm/MAINTAINER.md`), and a first look at flags found nothing: on the 206,791 scrimmage snaps of 2021 to 2026, a model of who is flagged (offense, defense, nobody) scored no better with the spread, the total, how far the offense is ahead of the spread, and the score against the total's pace than without them (+0.02%, 1 standard error, and the same in the last five minutes). That look didn't split by referee crew or by kind of foul. A predictor that does read them makes the game evaluator's comparison with the market mean less (`evaluators/game/README.md`).
- The clock: the data records the game clock at each snap and nothing in between. So the time teams let run before a snap or a timeout comes from the real gaps between snaps (`snap_gap` in the pre-snap and timeout priors) less the play itself (`shared.priors.PLAY_SECONDS`), and the hand-set durations of a play's parts are set to what real plays that stop the clock take. `game: plays` in `evaluators/game` is the check on all of it.
- Seasons: everything takes any season from 2011 on (`shared.nflverse.SEASONS`). What differs between seasons is handled in three places and nowhere else: the rules in `shared/rulebook` (the scenarios read every season-dependent value from it), the data's formats in `shared/nflverse` (every season comes out in one shape), and what earlier seasons can teach in `shared/priors` (pooled, older seasons discounted, and never across a rule change that the predictor ties its counts to).
- A rule change needs: the value in `shared/rulebook/rules.py`, the scenario reading it, a scripted test, and, if it changes how an event plays out, its fields in a group like `KICKOFF` with the affected priors keys tied to it.
- A scenario's outcome summary and the real outcome built from nflverse must have the same keys and meaning: `scenarios.play.summarize` with `shared/nflverse/contexts.py`, `simulators.game.summarize` with `shared/nflverse/games.py`. The challenge predictor reads a play through them, so it sees a simulated play and a real one the same way.
- A simulated play is the ruling after any replay review, as a real play is in the data. So a review never changes a play: a coach's challenge only costs what the rules charge for it (`scenarios/game/RULES.md`).
- What a coach decides by sending a unit out belongs to the lineups event, and what the unit then does to the snap event: a fake punt is the punt unit's (the real one too: `shared.priors.sent_out`), so the fourth-down decision and the fake don't overlap.
- Every evaluator scores with `evaluators.scoring` (fair CRPS for numbers, fair Brier for yes/no and categories), so scores mean the same thing at every level.
- The evaluators' run time is the development loop's: a predictor runs on every simulated play, so anything it works out that doesn't change from play to play (a roster's ranking, a table built from the priors) should be worked out once. `evaluators/MAINTAINER.md` says where the time goes and how to check a speedup changes no score.

## generated files (gitignored)

- .cache/nflverse/: downloaded nflverse files.
- .cache/lines/: downloaded player prop lines, one file per played game.
- .cache/training/: the trained predictors' training tables, one file per predictor and season.
- .cache/form/: each past season's totals per team, coach, referee, and player (what form is added up from).
- evaluation_output/: play evaluation, game evaluation, and betting lines reports.
- audit_output/: audit reports.
